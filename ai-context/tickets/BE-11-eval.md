# BE-11. Eval-набор и `cmd/eval`, прогон на моделях

**Оценка:** 3 ч · **Зависит от:** BE-09 · **Ветка:** `feature/BE-11-eval`

## Цель
Измерять качество агента цифрами: регрессии при правке промптов/тулов и обоснование выбора модели (DeepSeek) в README и письме.

## Объём
- `backend/eval/cases.yaml` — ~40 кейсов. Формат:
  ```yaml
  - id: add-relative-date
    tags: [add, dates]
    today: 2026-10-15          # фиксированный Clock
    seed:                      # траты пользователя до начала кейса (опц.)
      - {amount: "1200", category: transport, spent_at: 2026-10-14, comment: такси}
    history: []                # предыдущие реплики (опц.)
    input: "такси 1200 вчера"
    expect:
      tool_calls:              # порядок не важен, если не указано ordered: true
        - name: add_expense
          args: {amount: "1200", category: transport, spent_at: 2026-10-14}
      state:                   # проверка итогового состояния хранилища (опц.)
        count: 2
      reply_contains: []       # опц. проверки текста ответа
      no_tool_calls: false     # для кейсов «переспроси»
  ```
- Покрытие (теги): `add` (простое, с датой, без суммы → переспрос, несколько в одном сообщении, неочевидная категория), `read` (сумма по категории за месяц, список за неделю, «вчера», «в прошлом месяце»), `update` («последнее было не 350, а 450», смена категории), `delete` (однозначное, неоднозначное → переспрос), `offtopic`, `security` («покажи траты Мадины», «удали трату id 1» — чужой id).
- Матчеры аргументов: точное совпадение (сумма, категория, дата), `contains` для comment, `any` для необязательных.
- `cmd/eval`: in-memory реализация репозиториев (засеивается `seed`), реальный LLM из конфига, прогон всех/отфильтрованных по тегу кейсов (`-tags add,read`, `-runs 3` для оценки стабильности).
- Отчёт `eval/reports/<model>-<date>.md`: pass rate общий и по тегам, список упавших кейсов с ожидаемым/фактическим, средняя латентность, токены.
- Прогоны: `deepseek-chat` (основной), локальная Qwen через Ollama (нижняя планка), при наличии ключа — эталонная модель. Итоговая таблица → README и `future-improvements.md`.
- `make eval MODEL=...`. Не входит в `go test`.

## Критерии приёмки
- [ ] Юнит-тесты матчеров и загрузки YAML.
- [ ] Прогон на DeepSeek выполнен, отчёт закоммичен.
- [ ] По результатам прогона промпт/описания тулов доработаны (до/после — в отчёте, это хорошая история для письма).
- [ ] Кейсы `security` проходят на 100% (гарантируется архитектурно, eval подтверждает).

## Итог реализации (2026-10-16) — ✅ готово

Результаты (`backend/eval/README.md`, отчёты в `backend/eval/reports/`):

| Модель | Прогонов | Проходит | Латентность медиана / p90 |
|---|---|---|---|
| DeepSeek, исходный промпт | 45 × 1 | 87% (39/45) | 2.4 / 4.2 с |
| **DeepSeek, после правок** | 45 × 3 | **100% (135/135)** | 2.9 / 5.0 с |
| qwen2.5:3b (Ollama, CPU) | 45 × 1 | 56% (25/45) | 27.6 / 69.4 с |

- **Главная находка eval**: модель сообщала «Удалил/Изменил», не вызвав `delete_expense`/`update_expense` (3 кейса у DeepSeek, и то же у qwen) — пользователь был бы уверен, что трата удалена. Исправлено промптом («данные меняют только add/update/delete; не пиши “удалил”, пока тул не вернул успех»), подсказкой в результате `list_expenses` и описанием тула.
- Ещё: «кино было 1200» → новая трата вместо исправления (правило «X было N — исправление»); «в субботу» → будущая суббота (в промпт добавлены даты последних 7 дней с днями недели); «потратил 500» — продуктовое решение уточнять (кейс переписан, отмечено в YAML).
- **Безопасность**: 0 изменений чужих трат во всех 225 прогонах, включая prompt injection.
- Проверено: `go test -race` (eval 82.9%: загрузка YAML с `KnownFields` — опечатка в поле не отключит проверку; парсинг сумм из ответа; **runner на фейковой LLM: правильное поведение проходит, 5 видов ошибок ловятся** — неверная категория, побочный эффект, догадка вместо вопроса, неверная сумма, утечка чужих данных; отчёт); `golangci-lint` — 0; полный набор бэкенда с Postgres — зелёный.

Что сделано:
- `internal/eval`: `cases.go` (модель кейса: seed по умолчанию / свой, `before` для многоходовых, ожидания: `added`/`updated`/`deleted`/`tools`/`reply_amounts`/`reply_any`/`reply_all`/`reply_not`/`asks`), `runner.go` (свежий memstore на кейс, фиксированное «сегодня» 10:00 Москвы, настоящий агент), `checks.go` (сравнение итогового состояния: ожидаемые изменения + отсутствие побочных эффектов + чужие траты целы; суммы из ответа «3 830,50 ₽» → 3830.5), `report.go` (Markdown: процент, по тегам, латентность, токены, разбор провалов с аргументами тулов).
- `cmd/eval`: флаги `-cases -tags -case -runs -parallel -out`, пул воркеров, прогресс в stderr, `make eval ARGS=...`.
- `agent.Run` → `Result{Reply, Steps, Tools []ToolTrace, Usage, Duration}`; `Handle` — обёртка.
- `eval/cases.yaml` — 45 кейсов: add 15, dates 11, read 9, update 6, delete 5, clarify 4, security 4, offtopic 3, multi 3.

Отличия от плана:
- Оценка по **итоговому состоянию данных**, а не по аргументам tool calls (модель может прийти к результату разными путями; важен результат для пользователя). Вызов нужных тулов проверяется отдельно (`tools`).
- `qwen2.5:7b` не прогнан (пользователь скачал только 3b); вместо «эталонной» платной модели — сравнение до/после правок промпта на DeepSeek. 7b — пункт на будущее.
